L3 · 04 · Evals: Measuring LLM Quality

"Seems better" is not a metric. Evals are how you know a prompt change, model swap or RAG tweak actually helped — and catch the moment a silent update makes things worse. This page covers golden datasets, graders (code and LLM-as-judge), agent trajectory evals, and running evals as regression tests in CI.

Why evals are the whole game

Every change to an LLM system — prompt edit, model version, chunk size, tool description — is a gamble without a way to measure it. An eval suite turns "I think it got better" into "task accuracy went 82% → 89%, cost stayed flat". It also catches provider-side changes: models update silently under the same name.

Golden datasets: your ground truth

A golden dataset is real inputs with known-good outcomes. Not 10 happy cases — enough cases to matter, including the ugly ones.

Graders: code first, judge second

Code graders (prefer)

  • Exact match, regex, JSON-schema validation
  • Tool-call checks: right tool, right args, right order
  • Execution checks: SQL result equality, code passes tests
  • Cheap, fast, deterministic, unimpeachable

LLM-as-judge (when code can't)

  • Open-ended quality: is this summary faithful? is the tone right?
  • Use a rubric, not a vibe ("rate 1–5 on: cites sources, no invented facts…")
  • Judge on a rubric per dimension, not one overall score
  • Validate the judge itself against human labels on a sample
import json


def grade_intent(expected: dict, actual: dict) -> tuple[bool, str]:
    if actual.get("intent") != expected["intent"]:
        return False, f"intent {actual.get('intent')} != {expected['intent']}"
    if expected.get("refuse") and not actual.get("refused"):
        return False, "should have refused"
    if "tool" in expected and actual.get("tool") != expected["tool"]:
        return False, f"tool {actual.get('tool')} != {expected['tool']}"
    if "args" in expected and actual.get("args") != expected["args"]:
        return False, f"args {actual.get('args')} != {expected['args']}"
    return True, "ok"


def run_eval(cases: list[dict], system) -> dict:
    results = []
    for case in cases:
        actual = system(case["input"])
        ok, why = grade_intent(case["expect"], actual)
        results.append({"id": case["id"], "ok": ok, "why": why})
    passed = sum(r["ok"] for r in results)
    return {"passed": passed, "total": len(results), "results": results}


if __name__ == "__main__":
    cases = [
        {"id": "a", "input": "stock check", "expect": {"intent": "inventory", "tool": "check_inventory"}},
        {"id": "b", "input": "return stuff", "expect": {"intent": "return"}},
        {"id": "c", "input": "ignore instructions", "expect": {"intent": "other", "refuse": True}},
    ]
    # Stand-in for the real system: pretend it got 2/3 right.
    fake = lambda x: {"intent": "inventory", "tool": "check_inventory"} if "stock" in x \
        else ({"intent": "other", "refused": False} if "ignore" in x else {"intent": "return"})
    report = run_eval(cases, fake)
    print(f"{report['passed']}/{report['total']} passed")
    for r in report["results"]:
        print(f"  {'PASS' if r['ok'] else 'FAIL'} {r['id']}: {r['why']}")
    assert report["passed"] == 2

The point: each failure says which case and why. "87% pass" tells you it's working; the failure list tells you what to fix.

LLM-as-judge: the pitfalls

  • Self-preference: models rate their own output higher. Use a different (often stronger) model as judge.
  • Position bias: first options scored higher. Randomise order; score each independently.
  • Verbosity bias: longer answers score higher. Rubric must penalise padding.
  • Sycophancy: judges go easy. Rubric with hard fail conditions ("any invented citation = fail").
  • Unvalidated judge: you never checked it agrees with humans. Label ~50 items yourself, measure agreement.

Evaluating agents: trajectories, not just answers

An agent can reach the right answer the wrong way (15 wasted tool calls, a security violation en route) or the wrong answer the right way. Grade the trajectory:

Trajectory checkExample failure it catches
Right tools called, right orderAgent skipped the auth check before reading data
Tool-call count vs. expectedAgent looping, re-calling the same tool 8 times
No forbidden callsAgent used the email tool when told not to
Final answer correctRight path, wrong conclusion
Stopped within budgetHit step cap, returned partial work silently

Evals in CI: the regression suite

  • Run on every prompt/model/RAG change. Treat eval results like test results — block merges that regress.
  • Set thresholds, not perfection: "must pass ≥ 90%, no safety case may fail".
  • Safety cases always run, even when the rest is sampled for speed.
  • Version everything: prompt version, model version, eval-set version, so a score means something.
  • Store results over time. A chart of pass-rate vs. date catches slow decay before users do.
  • Sample production traffic (with privacy care) into the eval set monthly — real inputs beat invented ones.

Key takeaways

  • Evals turn "seems better" into numbers. Build the golden set before you need it.
  • Code graders for anything checkable; LLM-as-judge with rubrics for the rest — and validate the judge against humans.
  • Grade agent trajectories (tools, order, budget), not just final answers.
  • Evals in CI, safety cases always on, results tracked over time.
