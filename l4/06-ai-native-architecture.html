L4 · 06 · AI-Native Architecture & Build vs Buy

Adding AI to a product isn't like adding a normal feature: outputs are probabilistic, costs scale per call, the ground shifts under you monthly, and "it worked in the demo" is not an SLA. This page is the architecture-level view: designing AI-native systems, deciding what to build vs. buy, structuring a platform team, and reasoning about reliability and cost at the system level.

Why AI-native is different

Classic softwareAI-native software
Deterministic: same input, same outputProbabilistic: plausible-but-wrong is a normal outcome
Bugs are code errorsFailures are silent: a bad answer, not an exception
Unit tests prove correctnessEvals measure quality on a distribution
Cost scales with users (roughly flat/request)Cost scales per call with tokens — context length matters
Dependencies are stable APIsThe model under you updates silently
The central design consequence You can't prove an LLM feature correct; you can only bound its error rate. So AI-native architecture is architecture for uncertainty: evals as the test suite, guardrails as the type system, fallbacks as the error handler.

The reference architecture

The gateway is the key idea: one place where every LLM call passes through. Routing, budgets, guardrails, caching, tracing and fallback live there — not scattered across features. It gives you a single point to change models, enforce policy and observe cost, and it lets product teams use AI without each one reinventing the plumbing.

Build vs buy, at three levels

LevelBuy (API / platform)Build (self-host / own)
ModelDefault for most teams: frontier quality, zero opsWhen: data residency, volume cost, offline, custom fine-tune at scale
Serving/frameworkManaged platforms get you running fastWhen you outgrow their limits or need control (your own gateway, vLLM)
Feature (e.g. support bot)SaaS copilots for generic needsWhen it's your differentiator or needs your data/tools
Build vs buy drifts The answer changes over time. SaaS copilots add features; open models catch up; your volume grows until self-hosting wins on cost. Re-evaluate yearly — and design so a model is swappable behind the gateway, so "buy" never becomes "stuck with".

Designing for probabilistic output

  • Evals before launch (L3·04) and in CI — the acceptance test is a score, not "it ran".
  • Graceful degradation: when confidence is low, abstain, fall back to a smaller model, a rule, or a human.
  • Human-in-the-loop for consequential actions: design the approval step, not just the prompt.
  • Guardrails as a layer, not scattered prompt pleading (L3·08).
  • Idempotent tools so a retried tool call doesn't double-charge or double-book.
  • Version everything — prompts, models, eval sets — so "it got worse" is measurable and revertable.

The platform team pattern

As AI adoption grows inside a company, the winning structure is a small platform team that owns the gateway, eval infrastructure, observability and approved model list — while product teams build features on top. This is the same shape as internal developer platforms, with the same benefits (consistency, safety, speed) and the same risk (the platform becomes a bottleneck if it's mandatory and slow).

Cost and reliability at the system level

  • Cost model: cost per task = tokens × price × calls/task. Reasoning models and long contexts change it by 10–100×.
  • Vendor risk: a single provider is a single point of failure and a pricing hostage. Design the gateway so a second provider is a config change.
  • Reliability: LLM features inherit provider uptime + your model's error rate. SLA thinking applies: what does "available" mean when the answer can be wrong?
  • Data boundary: where does data go? Which providers retain it? For many companies this decides build-vs-buy more than price.

Key takeaways

  • AI-native = architecture for uncertainty: evals, guardrails, fallbacks, human approval.
  • Put a gateway between products and models: one place for routing, cost, safety, observability.
  • Build vs buy is per-level (model/serving/feature) and drifts — keep models swappable.
  • A small platform team enables product teams; don't let it become the bottleneck.
